# Changes and Feature List

## Version 2.2.1

* **Release candidate `2.2.1rc3` prepared.** This candidate contains the current Expert-Devices type editing and documentation changes on top of the `2.2.1rc2` release candidate.
* **Edit complete device types in one operation.** On the expert *Devices* page, **edit type** lists all instances of the same detected model across the installation. Each entry shows its name, gateway and address; YAML instances remain visible but cannot be changed. After selecting the instances, the normal device form shows mixed values as **different values**. Saving changes only fields which were actually edited, so all untouched fields retain their individual value on every device.
* **Release candidate `2.2.1rc2`.** This pre-release fixes teach-in EEP prioritisation and opens the Add device form with the selected EEP and device prefilled from the unknown-device popup.
* Replaced deprecated Home Assistant cover state constants with the `CoverState` enum.
* Cover position estimates now survive Home Assistant restarts, and the `eltako.invalidate_cover_position` service can explicitly invalidate an estimate after an external movement.
* **Release candidate `2.2.1rc1`.** This pre-release is intended for final testing before the stable `2.2.1` release.
* Updated the `eltako14bus` dependency to version `1.0.1`.
* Added twilight sensor support for EEP `A5-06-01`.
* Added the missing ELTAKO catalogue profiles `FIH65B` (`A5-06-02`) and `FFG7B` (`F6-10-00`).
* Updated the generated device documentation and catalogue tests.
* Added the fan platform for ventilation devices using `A5-38-08` (speed control) and `M5-38-08` (on/off).

## Version 2.2.0
* **The values of a telegram can be picked instead of guessed.** A profile field is the parameter of a class in the library, and its name alone says nothing: `state`, `command`, `movement`, `dimming_range` are plain numbers, and `mode = 112` is not something anybody types by accident. Every field now says what it is - a **choice with named options** ("on / off", "up / down / stop", "closed / open / tilted", "data telegram / teach-in telegram") or a **number with its unit and range** (°C, %, lx, m/s, 0.1 s steps for a cover). The tables live in `simulation/core/field_info.py`, next to the encoders they were read from, and the enums of a profile (the modes and priorities of `A5-10-06`) become their options by themselves - two members which share one code are one option whose label names both, because the telegram cannot tell them apart either.
  * **Only the fields which are really read** are offered: the central command writes completely different bytes for switching and for dimming, a weather station reports either wind or sun - picking the one decides the other fields, the rest disappear instead of promising a value which is dropped.
  * The free **"Send telegram"** form of the telegram page (expert view, next to the pause button) and the send fields of a device on the control page use the same renderer, so both offer the same names, units and ranges. A profile which can only be decoded says so instead of offering a form.
  * A test sends **every offered option of every profile** - an option which cannot be encoded would be a trap, and this is what would find it.
* **Teach-in telegrams can be sent by hand.** The "Send telegram" form of the live view could only send values; teaching something in meant using the teach-in button of a configured device or the simulation. It offers both teach-in telegrams as its own input modes now - and they run in opposite directions, which the form says instead of leaving it to be known:
  * **profile teach-in** - what a *sensor* sends to announce what it is: 4BS states function, type and manufacturer, 1BS clears the LRN bit, and RPS has no teach-in telegram at all, so a button press *and* its release are sent (the answer says `count: 2`).
  * **ELTAKO teach-in** - what a *sender* sends so that an ELTAKO actuator takes it into its memory, with the four data bytes of the sender profile (`catalog/teach_in.py`) - the telegram the teach-in button of a device produces. Offered for the four sender profiles which have one, and the form shows the data bytes it will send.
  * Both modes offer the **sender profiles the integration teaches in at all** (`EEP_WITH_TEACH_IN_BUTTONS` in `catalog/teach_in.py`), not every profile of the library - and a teach-in has no value fields, just the profile and the address it is sent from.
  * The telegrams are built by the encoders of the **simulation** (`build_teach_in_telegrams`), so a teach-in written by hand, the one of a simulated device and the one of the teach-in button are the very same telegram - only marked as outgoing (`as_outgoing`).
  * `eltako/send_telegram` takes a `mode` (`eep`, `teach_in`, `eltako_teach_in`, `raw`) and answers with `count`; the descriptor of `eltako/send_telegram_form` says per profile which teach-in it has.
* **The teach-in of a device is one button on its card - and a popup which says what it will do.** "This device does not react" is answered by two facts which stood nowhere: which gateway switches it, and with which address. The popup names both, offers the gateways the device can be moved to and does the whole change in one press. What that press is depends on the device, which is exactly what nobody should have to know: a device on the RS485 bus gets the address **written into its memory** (only a FAM14 can write, so it has to be connected), a wireless one **learns it from a telegram** - *Send teach-in* while it is in learn mode. In both cases the address becomes the sender of that device in Home Assistant, because otherwise the integration would keep transmitting the old one.
  * It replaced the dropdown which sat on the card itself: the current gateway, the address it hands out and the sentence which says what happens are what makes this usable, and none of that fits next to the state of a device. The card stays a card - a button, and the rest in the popup.
  * The button is only where the choice is real: not on a sensor (nothing switches it), not on a device out of `configuration.yaml` (it is changed there), and not when the installation has no gateway which could take the device over. A wireless device is only offered the gateways which transmit; a bus device can also stay on its bus, where the local senders `00-00-B0-xx` apply.
  * **The toolbar of the simple view lost two buttons**: *Search devices* - it is step 2 of the setup instruction, which is where somebody looks for it - and the teach-in dialog which briefly sat next to *+ Add device*. A search which can be started from three places looks like three different searches.
* **An actuator whose sender is missing offers to teach it in.** The control page reads out of the device memory whether the sender of Home Assistant is really in it (`sender_taught_in`, from the bus scan) and puts a **"teach in (missing)"** button in that row - without that sender no command ever arrives, which is the single most common reason for a device which does nothing. One click does what that kind of device needs: a device on the RS485 bus gets the sender **written into its memory** (`eltako/devices/teach_in`, the procedure of the EnOcean Device Manager, no hardware to touch), a wireless actuator gets the **teach-in telegram** it takes its sender from while it is in teach-in mode. Where nothing is known about the memory the button is offered quietly; where the sender is in it, no button appears.
  * The teach-in button **entities** are no longer listed on the control page: they carry the name of their device and do the same thing, so of two rows called "FSR14_4x ch1" the first one was a "Press" which explained nothing. The toolbar brings them back, and `enable_teach_in_buttons: false` removes them for good.
* **Every device can be sent a telegram by hand** - on the *Control* page, next to its normal controls: "telegram&hellip;" opens the values of its profile as input fields, prefilled with a usable start value, and sends them. Which telegram that is follows from the configuration: an actuator gets the profile of its **sender** (a relay does not listen to its own address - `A5-38-08` from `00-00-B0-01` is what switches it), a sensor or a contact its own profile, so a temperature of 21.5 °C or a rocker press can be produced without any hardware. It is the same encoder the simulation and the free send form use, so a hand written, a simulated and a real telegram are built by one piece of code.
  * The start values come from the profile, not from a row of zeros: `A5-04-02` opens with 21 °C and 45 %, `A5-38-08` with the switching command, `A5-10-06` with its mode and both temperatures - a form which can be sent as it is. A weather station (`A5-13-01`) needed a start value of its own: it sends two different telegrams and only `identifier` says which, `0` cannot be encoded at all.
  * A profile which the library can only **decode** offers no form instead of one which always fails - `A5-09-0C`, the air quality profile of the FLGTF, has no encoder. The descriptor says so (`sendable`), and a test insists that this flag tells the truth for every profile and that no *other* profile silently joins that group.
  * Tests pin the whole point of it: every EEP of the device catalog has fields **and** a start value per field, the start values really produce a sendable telegram, an actuator row offers the sender profile, a sensor row its own - and the rendered form carries the input fields and the send button.
* **On the *Control* page the device stands above its buttons.** The rows came in the order of the entity ids, so of the two rows called "FSR14_4x ch1" the first one was the **teach-in button** with its single "Press" - the light with On/Off stood fourteen rows further down, behind every button of the installation. That reads like the relay cannot be switched and the dimmer has no brightness at all. Inside a room the rows are now ordered by what they are for - lights, sockets, covers, heating, selections, then the buttons - and every row says its kind next to the name, because two rows of the same name cannot be told apart otherwise. A rendering test pins the order, the On/Off of a relay and the brightness slider of a dimmer.
* **The table of the *HA Entities* page is a table again.** Its rows had stopped being rows: the cells sat squeezed against the left edge instead of under the columns of their own head, and On, Off and "telegram&hellip;" stood underneath each other in a stack three rows high. The cause was in a completely different page. The panel puts the styles of **every** page into one `<style>` of its shadow root, so nothing is scoped - and the radio analysis styled `.controls { display: flex; flex-direction: column }` and `.control-row { display: flex }` for its filter boxes, while this page has carried exactly those two names on its `<tr>` and its `<td>` all along. Two `display: flex` and the table was no longer a table. The radio page now calls them `.radio-controls` / `.radio-control-row`.
  * **A test keeps the pages out of each other's stylesheets.** It resolves the css of every page the way the panel does (the shared constants of `lib/` are left out) and insists that each rule is anchored to at least one class no other page uses in its markup: `.type-chip.on` is fine, a plain `.controls` is not. The handful of rules which really do style shared markup are listed with their reason instead of being invisible.
  * While it was open: the table also got the card of `.table-wrapper` and a head, like every other table of the panel - it was the only one rendered as a bare `<table>`, so it sat on the page background without a border and its four columns carried no names.
* **Devices created in the web ui count as known everywhere.** The telegram analysis, the bus member view and the teach-in of the HA senders read the devices out of `configuration.yaml` only, so on an installation configured entirely in the web ui - which is what this version aims at - they saw nothing. The visible consequence: the **sender** addresses of those devices were unknown, and a sender is what Home Assistant transmits with. Every command it sent came back as the telegram of an unconfigured address and was offered on the pages as a **"newly discovered device"** - a FUD14 which switched perfectly was announced as a device to add, with an EEP "confirmed" by Home Assistant's own dimming telegram. On a bus gateway that is not even recognizable by eye: the sender `00-00-B0-01` appears on the wire as base id + offset (`FF-A2-24-00` + `00-00-B0-01` = `FF-A2-D4-01`), which reads like a device of its own. All three now read both sources through `get_devices_of_gateway()`, like the configuration check and the platforms always did.
* **The search of the simple view programs the actuators, not only the configuration.** A bus actuator only reacts to sender addresses which are in its memory - a device which was just found would be listed in Home Assistant and do nothing when it is switched. So the search writes them itself, right after it added the devices: the FAM14 which can write is connected in that moment, the bus is free again, and asking for a second button afterwards would be a trap for exactly the installation this search exists for. What an actuator refuses (a full memory, no answer) becomes a warning of the run instead of turning the whole search into a failure.
* **A bus scan which breaks off is continued where it stopped**, up to three attempts. Reading a bus takes minutes, and it can end in the middle for reasons which have nothing to do with the position being read: the serial connection dies, the port throws, the gateway goes quiet for a moment. Starting at position 1 again would read everything a second time - so the positions which are done are remembered and the next attempt visits only the rest. The counters say which attempt it is ("attempt 2/3"), because numbers which start low again otherwise read like a scan which lost everything.
* **The device table says who may switch each actuator.** A new column *Taught in* lists every sender which is in the memory of that device, each named by the gateway it belongs to - Home Assistant on this bus, a FAM-USB, a LAN gateway - and a sender which belongs to no configured gateway is shown as what it is instead of being hidden: a wall switch taught in with the PCT14 lives in the same memory. That column answers both directions of the question which costs the most time on a real installation: why does this light react to that switch, and why does it not react to Home Assistant.
  * **Single entries can be removed.** The `×` next to an entry clears exactly that memory line - the same thing the PCT14 does. The line is read again first and only cleared when it really still holds that sender, so a page which is a few seconds out of date cannot delete what moved into that line meanwhile; an entry whose memory line is unknown is shown but not offered for deletion. The stored memory image follows the write, so the table is right immediately instead of after the next bus scan.
* **"open device" is called "details" now - and stays in the panel.** On the *Devices* page the bus headings, the wireless gateway rows and a bus position with a configured device carried a button which jumped straight into the device page of Home Assistant: it left the panel for a page nobody had asked for, and in the [standalone runtime](docs/standalone/readme.md) it led nowhere at all. They open the **same popup** every other "details" of this ui opens (`frontend/lib/details.js`) - for a gateway: connection, port, base id, protocol, baud rate and how many devices talk through it; for a bus position: the device which sits there. The way into Home Assistant is one button **inside** that popup, offered where that page exists. So the answer to "what is this?" comes without leaving the page, and the jump is a decision instead of a surprise.
* **The add / edit form of the device page is a popup.** It is opened from all over that page - the toolbar, an unconfigured bus channel deep inside a bus section, an address which only sent telegrams, the details popup of a device - and as a block above the table it appeared where nobody was looking: pressing *edit* on a row far down the list scrolled the form into view, and after saving the row had to be found again. Now it opens in front of the page, which keeps its scroll position and its tables, and it closes the three ways every popup of this ui closes: the ×, *Cancel*, a click next to it. It is the same shell the details popup uses (`renderModal` in `frontend/lib/details.js`), so there is one popup in this ui and not a second one which looks almost like it.
* **Writing shows what it is doing and what is in there.** A teach-in writes a discovery and up to one memory line per actuator, which takes a while - so it has counters like a bus scan now ("actuator 3/14 - 00-00-00-05, 2 written"), with the same progress row and the same cancel button. And under every bus stands **who is already in the actuators**: one tag per gateway with "12/14", green when it is complete. A position whose memory was never read counts as **unknown**, not as missing - "not programmed" and "not looked at" are different answers, and only one of them is a reason to press a button.
* **The search of the simple view programs the connected wireless gateways as well.** Not only the sender addresses Home Assistant uses on the bus, but those of every connected FAM-USB, USB300 or LAN gateway - written while the FAM14 is there, because afterwards nobody can write them anymore. That is what makes the promise of the note above real: read and program once with the FAM14, then operate the installation with whatever is convenient. The result says how many addresses were written; what an actuator refuses (a full memory, no answer) is a warning of the run, not a failed search.
* **The senders of another gateway can be written into the actuators while the FAM14 is connected.** On the bus of a FAM14 (page *Devices*) there is a dropdown with the wireless gateways and a **program** button: every configured actuator gets the address of that gateway - its base id plus the last byte of the actuator address (`00-00-00-04` behind `FF-C0-02-00` becomes `FF-C0-02-04`), the rule the EnOcean Device Manager writes as well. Without it an installation cannot be moved from the FAM14 to a FAM-USB, a USB300 or a LAN gateway: a transceiver only transmits senders out of its own base id range, and only a FAM14 can write them into a device. The existing entries stay untouched - the actuator keeps reacting to what it reacted to before.
* **Which gateway switches a device is a choice now - per device, and it does both halves of it.** An actuator only reacts to the sender addresses in its own memory, and a transceiver only transmits senders out of its own base id range: an installation which is moved from the FAM14 to a FAM-USB needs the new address **in the actuator** *and* as the **sender of that device in Home Assistant**. Doing one without the other gives a device which is configured, listed and dead - so one command does both (`eltako/devices/sender_gateway`, `config/sender_gateway.py`), and it is offered where somebody stands when a device does not react: as a **"switched by"** picker in every actuator row of the expert device table and on every actuator card of the simple view.
  * **A bus actuator** gets `base id of the chosen gateway + the last byte of its own address` written into its memory - the rule of the EnOcean Device Manager. Only the addresses which are really missing go onto the bus: an actuator which already carries the one it is being switched to is changed in Home Assistant alone, which is why moving *back* to the bus (the local `00-00-B0-xx` of the FAM14, the default) needs neither a connected FAM14 nor a lock on the bus.
  * **A wireless actuator** has no memory anybody can write into - it learns the address which is sent to it while it is in teach-in mode. So there the picker is followed by a **teach in** button: the teach-in telegram of that profile goes out **through the chosen gateway** and its address becomes the sender of the device. Which address it is, is picked instead of derived: the offset the current sender has inside the range of its old gateway is kept (`FF-AA-80-05` becomes `FF-C0-02-05`), otherwise the first address of the new range which no other device already sends with.
  * **Nothing is switched over on paper.** A device whose actuator refused the write keeps its old sender and is named in the result, a device out of `configuration.yaml` is left alone (it is changed there) and said so, and an actuator outside the 128 addresses of a base id is reported instead of silently skipped.
  * **Step 4 of the setup instruction does it for the whole installation**: pick the gateway which is to operate everything from now on and every bus actuator is switched over in one go - the step which has to happen while the FAM14 is still connected.
* **The simple view says which gateway is needed for what - as four steps.** It is the one thing about an ELTAKO bus which cannot be guessed from a user interface, and it used to stand there as three paragraphs of prose which nobody reads twice. Now it is a numbered instruction on the start page: **1.** connect the **FAM14** by USB - only it reads the memory of the actuators and writes into it. **2.** press *Search devices* - it finds the gateway, reads every bus, adds what it recognises and writes the senders of Home Assistant into the actuators, without which nothing reacts to a command. **3.** check the list below and add with *+ Add device* what could not be identified for sure. **4.** optionally switch to an **FGW14-USB or a wireless gateway** for everyday use - running permanently on the FAM14 works technically but can be less stable, and a wireless gateway needs its senders programmed **while the FAM14 is still connected**. A step which is already done carries a checkmark instead of its number, so the list doubles as the progress of the setup instead of being a text to read again on every visit. **Two of the steps carry the button which does them**: the search sits in step 2, and step 4 has the gateway which is to operate the installation from then on - a step which only says what to press somewhere else is a step people get wrong.
  * It is called **Initial Setup**, stands at the **very top** of the simple view - above the gateways and the devices, because it is the first thing a fresh installation needs - and it **folds away**. Folded it is one line with the progress ("3/4"), and it stays folded: the state lives in the browser (`localStorage`), so it survives a reload, a page change and the redraws this page does on every state change. A fresh browser gets it folded out.
  * **Every gateway is in the list of step 4**, the ones on the bus included - not only the wireless ones. Whichever gateway is to carry the installation, Home Assistant has to send with **its** addresses, and that half is a change of the configuration in either direction: away from the FAM14 it is `base id + last byte of the actuator address`, back onto the bus it is the local `00-00-B0-xx` again. Offering only the wireless gateways made the way back invisible, although it is the way out of every wrong choice. The gateway which carries the installation right now is preselected, so the list says what is set instead of proposing a change nobody asked for.
  * **Written is only what is missing.** An actuator which already carries the address - the memory image of the last bus scan says so - is switched over in Home Assistant alone. A run in which nothing is missing therefore touches the bus not at all: no lock, no minutes of waiting, and **no connected FAM14**. That is what makes the way back usable at all, because the local senders have been in the memories since the search; an installation which runs on an FGW14-USB can move back onto the bus without plugging the FAM14 in again. Where an address really is missing the FAM14 is still required and said so - the button is no longer disabled for the cases which do work. A memory which was never read counts as missing, and the actuator checks it itself before anything is written.
* **There are release candidates now** - a version like `2.2.0rc1` which can be installed and used like a release, but is not one. It is published as a github **pre-release**, so HACS hides it until *show beta versions* is switched on for this repository: nobody gets it by accident, and an installation which only takes releases stays where it is. On PyPI the same marker makes it a pre-release for pip, so `pip install eltako-enocean-tool` keeps installing the last finished release and only `--pre` takes the candidate.
  * **It is visible in the running integration**, not only in the release notes: the version in the header of the web ui carries a `pre-release` tag on every page, and the *About* page says what that means, that it can contain bugs a release does not have, and how to get back to a release. A tester should never have to remember which version they are on.
  * The [build pipeline](.github/workflows/build_package.yml) refuses both ways to get it wrong: a version with a marker on a release which is *not* marked as a pre-release (HACS would offer it to everybody), and a finished version on a release which *is* marked as one (nobody but a beta tester would ever see it). How to create one: [installing a specific version or branch](docs/install-specific-version-or-branch.md).
* **The "Eltako" lettering stands as a watermark behind every page** - large, centred and barely a shade away from the page background, the way a letterhead carries it. It is the lettering of the official logo without the blue square around it (`img/eltako-watermark.svg`, cropped to its bounding box) and it is drawn as a **css mask** filled with the brand colour, not as a fixed grey image: on a dark theme it switches to the lightened blue, so it stays the same faint shade instead of disappearing. It sits behind the content (`.shell::before`), never scrolls with the page and takes no clicks; the url is handed to the stylesheet as `--eltako-watermark`, because a relative url inside it would be resolved against the Home Assistant document instead of the frontend folder.
  * **The tables are slightly translucent** so it shows through them - they are the largest surface of the page and would otherwise cut the lettering in half. Their card colour is *mixed* with transparency (`color-mix`, 60 %), so a custom or dark theme keeps its own surface - and 60 % is what really makes the lettering readable through them: the watermark is 5 % strong, so a nearly opaque table leaves a difference of one percent, which exists in the css and not on the screen. The text of the table is opaque and keeps its contrast. The sticky table head stays opaque on purpose: the rows scroll underneath it and would ghost through a translucent one.
* **One silent bus position no longer ends the whole scan.** `eltakobus.error.TimeoutError` shares only its *name* with the builtin - it inherits from `Exception`, so `except TimeoutError` never caught it, and the library raises exactly that whenever the gateway answers with an EltakoTimeout telegram ("the addressed device did not answer"), which is the normal reply for a gap in the bus or for an answer which arrived damaged (`ParseError: No preamble found`). The scan then died at that position and everything behind it stayed unread - looking exactly like a scan which hangs. Every position is guarded now: a position which does not answer, or whose answer cannot be read, costs that position and is named in the log; the rest of the bus is read.
* **A bus operation can be cancelled - and the bus is released even when it cannot be reached anymore.** A scan reads every position and every memory row of an RS485 bus; that takes minutes, holds the bus and queues every command of Home Assistant meanwhile. If such a scan hangs - the serial write runs into a timeout and its thread never reaches its own cleanup - the bus stays locked, nothing switches, and from the outside that looks exactly like a scan which is simply slow. The web ui now has the way out: **cancel & release bus**, in the activity banner of every page and next to every bus on the device page.
  * **It does two things, because two different failures have to be cured.** The running loop is asked to stop between two bus requests - the clean end, which unlocks the bus in the library and lets reception continue. And the lock is released **regardless**, so the commands which were waiting go out immediately instead of being dropped after 20 seconds.
  * **It can be pressed at any time**, also when nothing appears to be running. That is the point: a hanging operation and an idle bus are indistinguishable from the outside, and a button which is disabled exactly when it is needed is no button. When nothing was running the answer says so instead of pretending to have fixed something.
  * **A cancelled operation cannot take the bus away from the next one.** The thread of a hanging scan runs its `finally` whenever its serial call finally returns - minutes later, when somebody has long started a new scan. Every acquisition therefore carries a generation number and a release which names an old one is ignored.
* **The simple view shows one progress bar instead of two.** While devices are searched, the activity banner of the panel stands directly above the white card of the start page and already lists every bus with its counters - the card below repeated the same bars a few pixels further down, which reads like two operations instead of one. The card keeps its words (what is happening, that the devices do not react meanwhile, how many devices were found so far), the bars belong to the banner.
* **The web ui shows the log of the integration** - new page *Logs* in the expert view. The answers this integration produces are in the log ("did the command go out?", "why did the scan stop?", "which telegram could not be decoded?"), and the log is the hardest thing to reach: file access or the Home Assistant log viewer, mixed with every other integration. The records of the `eltako` logger are now additionally kept in a ring buffer in memory and shown here - newest at the bottom like `tail -f`, with the time to the millisecond, the level, the child logger and the traceback of an error, filterable by level and by text (the search runs in the backend, so it finds records which are not on screen) and downloadable as a text file.
  * **The log level is set on the same page.** A log which does not contain the answer is worth nothing, and switching to `debug` meant editing `configuration.yaml` and restarting until now. Here it takes effect immediately, is remembered across restarts, and `inherit` gives it back to the `logger:` section of Home Assistant. Deliberately *not* through the normal settings path: that reloads every gateway config entry, which closes the serial ports - the last thing anybody wants while they are debugging a bus.
  * Nothing is redirected: the buffer is a handler **next to** the ones Home Assistant installed, so the log file keeps everything it had. The page says how many records already fell out of the buffer instead of pretending its oldest line is the beginning.
* **While a bus scan runs, nothing else talks on that bus.** A scan, the teach-in of the HA senders, the reading of the device memories and the base id request of a FAM14 all lock the RS485 bus and switch reception off while they ask every position in turn - and a switch command which went onto the wire in between corrupted exactly those answers: positions came back empty, devices looked missing, the memory image was incomplete, and the cause was invisible because both sides looked like they had worked. The gateway now hands the bus to one operation at a time (`try_acquire_bus()` / `release_bus()`, `with gateway.exclusive_bus_access(...)`).
  * **Commands wait instead of disturbing.** A telegram which Home Assistant wants to send while the bus is busy - a light, a cover, a simulated device on that gateway - is queued and sent the moment the bus is free, so a light switched during a scan still goes on afterwards. Only what waited longer than 20 seconds is dropped rather than arriving minutes late, and the log says how many were dropped: a cover which starts moving long after the click is worse than one which did not move at all.
  * **A second operation is refused, not queued.** Two scans, or a teach-in during a scan, are a mistake and not a queueing problem, so they are answered with `already_running` and the name of what is running. The bus is taken **before** the scan thread starts - the old check-then-start left a window in which two clicks in the same moment both passed. A device test does not start at all while the bus is busy: it measures answer times, which a queued telegram would falsify.
  * **The web ui says what is going on.** The bus scan buttons of a gateway are disabled with the reason ("scanning bus", "teaching in the senders") instead of the fixed "scanning bus...", because it can be the teach-in or the base id request as well; `eltako/bus/members` delivers it per gateway (`busy_with`).

  * The detection runs **once a day** by default (`plug_and_play_interval: 1440`, plus once a minute after a restart) and can be set to anything between hourly and weekly, or to 0 for "only when the button is pressed". Probing opens every free serial port and a bus scan locks the bus, so a tighter interval buys nothing - a gateway is plugged in rarely, and for that moment there is the button.
  * A port whose usb descriptor is known but fits no ELTAKO/EnOcean gateway (Zigbee/Z-Wave sticks, ...) is not opened at all; a port without a descriptor is probed, because inside a container only the device nodes are passed through. A stick which another program holds open cannot be opened twice, so it is skipped by the probe itself.
  * **Bus**: a bus gateway gets its bus read once (discovery plus the complete memory of every device - the same paced scan as the button on the device page). Reading it locks the bus for minutes, therefore the periodic check skips a bus which was already scanned; re-reading is the explicit second button.
  * **Devices**: added are only those which are unambiguous - a bus position whose discovery reply names a model which maps to exactly one device class and which the device catalog knows (one device per channel of a multi channel device, sender ids `00-00-B0-<position>` like the EnOcean Device Manager uses), a sender which was found in the memory of a bus actuator (its key function names the EEP) and an address which sent a 4BS teach-in telegram (the telegram states the EEP). Everything else - position not identified, model shared by several device classes, EEP only guessed from the data bytes, actuator which needs a sender to be taught in - is listed as "needs a decision" with its reason and stays a manual step on the device page.
  * Detected devices are stored like devices created in the web ui, so **their attributes can be changed and they can be removed again**. Nothing is written into any device: the sender ids of added actuators still have to be taught in ("check & teach in HA senders").

* Bugfixes for reported issues
  * Restoring the last value of a counter (`state_class: total_increasing`, e.g. an electricity meter) failed with `ValueError: invalid literal for int() with base 10: '36231.4'` and Home Assistant dropped the entity. States are strings and can contain decimals, so they are parsed as number now and only narrowed to int if there is no fractional part (`config_helpers.parse_number_state`). Applies to `measurement`, `total` and `total_increasing` alike. ([#175](https://github.com/grimmpp/home-assistant-eltako/issues/175))
  * No more false `Maybe have wrong device id configured!` warnings for gateway and metadata entities. Gateway diagnostics, info fields, event listeners and the repeater mode use the base id or `00-00-00-00` by design, but were validated as actuators (`_attr_is_actuator_entity = False` marks them now). In return the **sender ids of actuators are really validated**: light/switch/cover/climate store it as `_sender_id`, which the check never looked at - a sender id outside the base id range of a transceiver (the gateway silently drops those telegrams) went unnoticed. The warnings name the offending address, the gateway type and the expected format, and the sender id is not validated while the base id of the gateway is still unknown. ([#203](https://github.com/grimmpp/home-assistant-eltako/issues/203))
  * The `gateway_<id>_send_message` service accepts the sender address as `id`, `sender_id`, `sender` or `address` and as string (`FF-A7-96-82`) or number (`0xFFA79682`). Only `id` was read before, so the natural guess `sender_id` ended in `No valid sender id defined. (Given sender id: None)` and nothing was sent. A sender id outside the base id range of the gateway is reported as warning now (usual cause of "nothing happens"), a wrong eep no longer produces a misleading message about the sender id, and values which do not fit the eep are reported instead of crashing the service call. ([#194](https://github.com/grimmpp/home-assistant-eltako/issues/194))
  * Tilting slats does not block Home Assistant anymore: the wait between the move and the stop telegram used `time.sleep()` in a worker thread (up to 25 s per call) and crashed with a `TypeError` if the tilt position was unknown after a restart. It is `async_set_cover_tilt_position` with `asyncio.sleep()` now, and an unknown position is taken from the end position of the requested direction.
  * Covers: the runtime of a full travel (`time_opens`/`time_closes` + 1 s) is capped at 255, the maximum the telegram can carry - with a configured runtime of 255 s encoding the telegram failed. Setting an intermediate position while the position is unknown is rejected with a clear warning instead of a `TypeError`; 0 and 100 still work and recalibrate the cover. ([#103](https://github.com/grimmpp/home-assistant-eltako/issues/103))
